# Mission 4: choices ledger

Decisions the autopilot made that the spec and plans left open, judged
after each slice (audit-choices). Banked entries are givens for later
slices.

## Slice 1 (PR #92)

Review these first: 1.3 (what open information hides) and 1.5 (losses
not shown to the enemy at all).

### Needs Brian (provisional call in place)

**1.3 Open information still hides the owner's secrets.** A group that
creates a game with "open information" (spec: a per-game option) sees
the enemy's counters whole: TOE, cohesion, CP, dummies as dummies. Still
hidden, as the hot-seat browser already hid them: supply loads,
motorisation points, repaired points, whether an unrevealed minefield is
real, what a project builds, and sealed answers until revealed. The spec
said open information makes the enemy columns equal the own-side ones.
*Gap:* the spec did not know hot-seat already hid these. *Reach:* what
an open-information game shows. *Provisional call:* keep them hidden
(hot-seat unchanged); to reverse, skip layer 1's owner-secret block in
`view_for` when `open`. *Confidence:* medium.

### Sound

**1.1 Aliases are a keyed hash, not a numbered permutation.** An enemy
supply unit's id `supply:axis:dummy-3` reaches the Commonwealth as
`supply:axis:s<16 hex>`, the SHA-256 of the per-game key and the real
id. The plan said numbers `s1, s2, …` from a shuffled list; but supply
units arrive (convoys, reinforcements) and die during a game, and a
shuffled list re-deals every alias each time. *Reach:* slice 2 stores a
32-byte `alias_key` per game; aliases are long in any UI that shows
them. *Confidence:* high.

**1.2 Orders are un-aliased by walking their JSON.** The plan asked for
an exhaustive `match` on `Order`; instead every string in the order's
JSON that looks like an enemy alias is mapped back, and a string that is
an enemy's *real* supply id is refused (naming one means probing). No
order variant, present or future, can be missed. *Reach:* the server
un-aliases every input this way. *Confidence:* high.

**1.4 Enemy pieces are an allow-list.** `view_for` keeps only the
fields in `ENEMY_PIECE_KEEPS` (the counter face and board markers:
`contact`, `engaged`, `reserve`, `garrison_of`); every other field, and
any field added later, is hidden from the enemy until someone lists it.
A test fails when a `GameState`, `Piece` or `CombatSegment` field has no
row. *Confidence:* high.

**1.5 Stricter than the spec on combat events.** The spec said an
enemy's losses are "reduced to losses in hex"; the engine shows the
other side no `losses`, `disorganised` or combat-CP event at all,
because 3.61 reveals "not numbers or which weapons were lost". The other
way round, `barrage.points` (the points landing on a target) is kept,
because 12.0 says the target is told the actual points; the firers are
not. Anti-armour fire shows the target side no points. Open questions
are posted to cna (PROGRESS, *Requests for cna*). *Reach:* slice 4's
panels show "?" for what is gone. *Confidence:* medium.

**1.6 POW and guard numbers are their owner's.** `GameState` called
prisoner points open information (28.1x), but cna's 3.61 table says
"POWs, camps, guards: numbers secret", so the enemy's `prisoners`,
`prisoners_out`, `prisoners_off_map` and `guards` are removed.
Escapees stay shown to both. *Confidence:* medium.

**1.7 A finished game hides nothing.** Once `over`, `view_for` shows
everything bar `log` and `rng` to every viewer (the spec lets `save`
out then). This also keeps hot-seat's end screen as it was. Events stay
redacted. *Confidence:* high.

**1.8 Preview refuses during sealed steps.** Beyond the plan's dice
rule, `preview` answers `{"hidden": "sealed"}` whenever a sealed step is
pending, since the answer that completes a step would show the other
side's. No UI path previews then. *Confidence:* high.

**1.9 Golden hashes live in files.** `tests/games/<name>.sha256`,
written by the regenerate tests, replace the constants pasted by hand
into `golden.rs` (AGENTS.md's bump steps updated). *Confidence:* high.
